## 1. What we're building

Fetcher 1.0 already works end-to-end: a floating bubble sits on top of TikTok/Instagram, user taps it, the current video downloads in the background (notification progress), and it lands in Downi's Vault. **That flow does not change.**

What changes in 2.0 is the bubble itself — replacing the current plain circular icon with "the Core": a physical-feeling obsidian-gel orb with a cyan energy membrane and an embedded chevron, matching the attached design reference exactly (files: Core v2 spec, sheets C2–C6).

The Core must reproduce:
- **Base look:** glossy black gel sphere, translucent cyan rim/membrane, chevron (▶-like folded ribbon) centered, subtle top-left glossy highlight, soft drop shadow under it (floats above the host app).
- **Sizes:** 48dp / 56dp / 64dp variants — pick one default (56dp) for launch, keep the token so it's easy to change.
- **C2 — Wake sequence:** dormant → aware → ready over ~600ms when Downi detects a supported video is on screen (energy builds from within the gel, not layered on top).
- **C3 — Touch physics:** press-and-rebound (~10% compression + overshoot on tap), drag-follow with slight chevron lag (~4px), edge-snap on release (compress on contact axis, bulge perpendicular, glide to rest).
- **C5 — Progress ring:** the outer cyan ring fills 0→100% as real download progress, not a timer. Idle/active states get a subtle sheen/comet/breathing motion. Pause = frozen ring, no motion. Resume = ring picks up from where it paused. Complete = energy pulls inward to center, brief bright merge, then settles.
- **C6 — Failure/retry:** on failure, energy shifts to a muted rose color (not red), chevron stays visible, no flashing/error icon — "quiet, not broken." Tap-to-retry does a press/rebound and transitions rose → teal as it re-resolves. A separate muted blue/gray "unsupported" state (link not from TikTok/Instagram, or can't be resolved) with no red anywhere.

**Not in scope for the Core widget:** particles, sparks, extra icons/badges, alarm/error iconography, shape changes between states. Same silhouette and material throughout — only internal energy/light/color change.

## 2. Why Lottie, not custom Canvas/Compose drawing

Cline — read this before writing any rendering code.

The gel/glow/squish look in the reference images is achieved through layered gradients, blur, and organic deformation. Hand-coding that in Canvas/Compose per state is slow to get right, hard to keep "identical" across 7+ states, and fragile across model swaps (Kimi/DeepSeek/MiMo) since each will interpret "make it look glossy" differently.

**Approach: pre-built Lottie animation files + a thin Kotlin state machine that plays/blends them.**

- Mansoor (or whoever does the visual asset work) builds the Core animations once in After Effects (Bodymovin plugin) or a Lottie-compatible tool, exporting small JSON files.
- The app just loads and plays the right JSON for the current state — no custom drawing code for the look itself.
- Drag physics (finger-follow, inertia, edge-snap *position*) is the one part that must stay in code, because Lottie files can't respond to live touch coordinates. Keep this to a small, isolated `CoreDragController` — plain spring/decay math, no rendering logic mixed in.

This split means Cline's job is almost entirely "plumbing" (state machine, WindowManager overlay, touch handling) rather than recreating gel-physics rendering from scratch — much more reliable output from a free/small model.

### If Lottie assets aren't ready in time

Ship a **static-state fallback** first (each state = one drawable/PNG or a simple crossfade between two Lottie files: idle-loop and progress-ring), then swap in full animated Lottie files once they're built, without changing any of the state-machine or overlay code. Don't block the whole 2.0 launch on having all 7 states fully animated — sequence this as milestones in section 5.

## 3. Architecture

```
core/
├── CoreOverlayService.kt       # foreground service, owns the WindowManager overlay window
├── CoreView.kt                 # the floating view: LottieAnimationView + touch handling
├── CoreStateMachine.kt         # enum states + transition rules + which .json/asset maps to each
├── CoreDragController.kt       # spring physics: follow finger, inertia, edge-snap
├── CoreDetector.kt             # (existing Fetcher 1.0 logic) detects TikTok/Instagram video on screen
└── assets/core/
    ├── core_dormant.json
    ├── core_wake.json          # dormant -> ready, plays once on detection
    ├── core_idle_ready.json    # looping breathing/sheen while waiting for tap
    ├── core_press.json         # press + rebound, plays on tap-down/up
    ├── core_progress.json      # ring driven by setProgress(0f..1f), not autoplay
    ├── core_pause.json
    ├── core_complete.json      # energy-pull-in + merge, plays once
    ├── core_failure.json       # teal -> muted rose
    ├── core_retry.json         # rose -> teal (press + rebound variant)
    └── core_unsupported.json   # muted blue/gray, subtle response
```

### State machine (CoreStateMachine.kt)

```
DORMANT -> AWARE -> READY        (on video detected; C2 wake sequence)
READY -> PRESSING -> DOWNLOADING (on tap; C3 press/rebound, then ring starts)
DOWNLOADING -> PAUSED            (on user pause)
PAUSED -> DOWNLOADING            (on resume; C5 resuming sequence)
DOWNLOADING -> COMPLETING -> READY-or-DORMANT   (on finish; C5 completing, then fade per C5.7)
DOWNLOADING -> FAILED            (on error; C6 failure, muted rose)
FAILED -> PRESSING -> DOWNLOADING (on retry tap)
READY -> UNSUPPORTED -> READY    (tapped on a non-TikTok/Instagram/unresolvable link)
* -> DORMANT                     (video leaves screen / app backgrounded)
```

Keep this as an explicit sealed class + `when`, not string flags — with 7+ states and free-model-assisted edits, implicit state via booleans will drift and produce impossible combinations (e.g. "paused" and "failed" both true).

### Touch handling split

- `CoreView` owns the `WindowManager.LayoutParams` and forwards raw touch events.
- `CoreDragController` decides: is this a tap (→ state machine PRESSING) or a drag (→ update overlay x/y with spring-follow, then on release run edge-snap animation to nearest screen edge)?
- Threshold: if finger moves less than ~8dp before ACTION_UP, treat as tap, not drag — avoids accidental drags eating taps.

## 4. Key integration points with existing Fetcher 1.0 code

Since 1.0 already works, don't rewrite the detection/download pipeline — only replace the bubble's View/UI layer and wire its existing callbacks into the new state machine:

| Existing 1.0 signal | Drives Core state |
|---|---|
| Video detected on screen | `DORMANT -> AWARE -> READY` |
| User taps bubble | `READY -> PRESSING -> DOWNLOADING` |
| Download progress % (already feeds notification) | `CoreView.setProgress(pct)` while `DOWNLOADING` |
| User pauses (if supported) | `-> PAUSED` |
| Download success | `-> COMPLETING -> READY/DORMANT`, also existing Vault-write logic unchanged |
| Download error | `-> FAILED` |
| Tap on unsupported link | `-> UNSUPPORTED -> READY` |

If Fetcher 1.0 doesn't currently expose a clean progress callback/percent to the bubble (only to the notification), that's the one piece of "real" logic work here — add a shared progress emitter both the notification and CoreView observe.

## 5. Build order (milestones for Cline)

Do these in order — each is independently testable on-device before moving to the next:

1. **Static Core, no animation.** Replace the current bubble drawable with a static PNG/vector of the Core (idle/ready look). Confirm overlay position, drag-to-move, edge-snap-on-release all still work exactly as 1.0 did. *(De-risks the WindowManager/touch layer before adding Lottie.)*
2. **Lottie plumbing.** Swap the static image for a `LottieAnimationView` playing `core_idle_ready.json` on loop. Confirm it renders correctly at 56dp on the vivo test device (check for scaling/aliasing issues at small size).
3. **State machine wiring.** Implement `CoreStateMachine`, wire real Fetcher 1.0 callbacks (table above) to it, and swap Lottie files on transitions — even with placeholder/rough animations at this stage. Goal: prove every transition fires correctly end-to-end.
4. **Progress ring.** Wire real download percentage into `core_progress.json` (or programmatic ring draw if Lottie progress-driving proves awkward — test both).
5. **Touch physics polish.** Press/rebound on tap, drag lag, edge-snap easing — C3 behaviors.
6. **Failure/retry/unsupported states.** Wire error paths last since they're least visited in normal testing — don't let them be an afterthought just because they're rare.
7. **Final device pass.** Manual test on vivo V2058: rapid tap-retap, drag during active download, screen rotation, backgrounding TikTok mid-download, low-end thermal throttling (animation jank check).

Do not let Cline batch all 7 milestones into one commit/session — test and confirm each on-device before the next, same as the v3.1 stabilization approach.

- **The material is now the owner's own sheet.** `tools/core_sheet_extract.py` (new, reproducible, PIL-only) lifts the orb out of `test_out/refs_v33/C1.png` — the hero render for the ready/idle look, C1's state row for the paused look — into `res/drawable-nodpi/core_orb.png` + `core_orb_paused.png` (512 px RGBA, transparent). Its own gate reports **0 stray annotation islands**: the sheet's leader lines, their dots, the dashed touch circle and the studio drop shadow are all out of the alpha (the drop shadow is recognised as *colourless*, the orb's own light as saturated-or-bright).

### Deviations from the plan text (each deliberate)

1. **Java, not Kotlin.** The module has no Kotlin toolchain (only `com.android.application` + Chaquopy); adding it means a new plugin + compiler/stdlib artifacts and a rewritten build for zero visual gain. The plan's `core/*.kt` maps to `downicore/*.java`, shape unchanged (explicit state machine, isolated drag/physics, art-not-code). Say the word and Kotlin can be its own step.
2. **Static-first, exactly as §2 allows.** Lottie is not in the local Gradle cache and the JSONs do not exist; the plan's own fallback is what milestone 1 is.
3. **The chevron is baked into the art for now.** So `Look.mark` / `markSink` no longer dim or sink it during a download, and `setMarkLag` rides the whole pebble instead of the chevron. Both return when the Lottie stage splits the chevron into its own layer (M2); `downi_core_mark*.png` is kept unused for exactly that.
4. **Rose / muted blue-grey are derived, not hexed.** §6 left those open, so `CoreTint` derives them from the sheet's cyan (187° → 350° + desaturation). If §6's hexes arrive they replace two constants.
5. **Default Core size is 64 dp — now a confirmed ruling, not just a default.** §6 recommended 56 dp, but the owner ruled **64 dp** on 2026-09-27 after the live 48/56/64 comparison (`test_out\core_visual_m2b\_review_sizes.jpg`), so `DowniCore.DEFAULT_SIZE_DP` stays where it was and no code changed. `setSizeDp()` / `core.cmd size <dp>` still drive all three live.
