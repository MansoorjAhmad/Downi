# V3.2 PLAN — DOWNI Fetcher (floating zero-touch downloader)

**Status: DOWNI CORE PLAN ACTIVE — Phases A–G approved by the owner 2026-09-25 (rulings D1–D5
below).** Phase 1 bubble shell is built and B1–B4 are observed on device. B6's death is explained
(vivo `com.vivo.pem` → `action.vivo.powercontrol` → `com.vivo.abe` force-stop) and a foreground
service landed, but it only *doubles* survival. The 2026-09-25 A/B soak closed the app-side lever:
with `RUN_ANY_IN_BACKGROUND: allow`, Instagram foreground and scrolling, the process still died in
~4 min — **no app-side lever left**; only the user-side exemption remains (B6 block below,
`V3.2_SESSION_CONTEXT.md` §6/§7).

Next: **Phase A — Core shell + visual states (VISUAL GATE).** Nothing interactive, nothing detecting,
nothing downloading is written until the owner has seen the rendered states and the 48/56/64 dp mark
comparison.

## The feature (owner spec)

> Open Instagram/TikTok → floating bubble appears → video detected → bubble becomes
> ready → tap → download starts → progress stays synchronized with Downi, notification,
> Queue, and Vault.

## Locked rulings (2026-09-24, do not relitigate)

1. **Zero-touch required** — no copy-link, no share, no leaving the platform app.
2. **IG + TikTok only, videos only** (photo posts permanently out of scope).
3. **Tap-to-fire** — the bubble never downloads on its own.
4. **Pipeline is read-only reuse** — a resolved source goes through the existing
   `DowniDownloadService.startShared(context, url)` → Queue → notification → history →
   Vault (same saved file, no duplicates). The engine is not modified.
5. **Screenshots/visual analysis = spike diagnostics only**, never the production path.
6. **Local only** — accessibility data and spike logs never leave the phone; logs are
   deleted after analysis.
7. **Honesty rule** — if detection cannot be made reliable, we report exactly what
   failed; the bubble may never pretend to be armed when it isn't.

## Architecture (owner spec + layered-detection design, reconciled 2026-09-24)

```
AccessibilityService
 ├─ Layer 1: package detect (IG/TikTok foreground) → bubble appears (Phase 1)
 ├─ Layer 2: accessibility tree inspect → VideoCandidate {platform, id?, url?, confidence}
 │            └─ nothing found → bubble stays idle (honest, no fake armed state)
 └─ Layer 3: screenshot = Phase 0 diagnostic fallback only
TAP → SourceResolver(candidate)                 (Phase 2)
 ├─ resolves → DowniDownloadService.startShared → bubble ring ⇄ notification ⇄ Queue ⇄ Vault
 └─ fails    → bubble says "Couldn't detect this video" (plain sentence, house rule)
```

**Requirement split (the key insight):** "know I'm watching a video" (Layer 1–2, cheap)
is NOT "obtain the downloadable URL" (Layer 2–3, the unknown). Phase 0 measures the
unknown before anything is built.

## Phase 0.5 — Chain test: can DOWNI drive the platform's own share flow? (added 2026-09-25)

**Why this exists (owner ruling 2026-09-25):** the Fetcher is its own feature and gets built —
it is not a DowniDrop variant. Phase 0 measured that neither Instagram nor TikTok ever exposes
a URL/ID in the accessibility tree (61/61 dumps clean, on-device), while both expose the
**Share control** and reliable watching signals. So the Fetcher's resolution step will be
DOWNI *itself* driving the platform's own share UI:

> tap bubble → DOWNI clicks **Share** inside the platform app → the platform's share UI opens
> (≈1 s, visible) → DOWNI selects **Copy link** (clipboard relay) or DOWNI itself in the share
> sheet → the real deep-link URL enters the existing `startShared()` pipeline → grab starts.

Every locked ruling still holds *for the user*: they never copy, never share, never leave the
platform app. The ≈1 s share UI flash is the measured, disclosed cost of the mechanism.

**B6 blocker — SOLVED (2026-09-25):** the process death was not our bug. The vivo Application
Behavior Engine force-stops backgrounded apps, and that also wipes
`enabled_accessibility_services`, so nothing could revive us:

```
09-25 10:15:48.265 I am_kill : [0,11208,com.omnidownloader.app,100,stop com.omnidownloader.app due to stop by com.vivo.abe]
```

Crash buffer clean since 09:01:31, heap 2–8 MB of 256 MB, device-idle-whitelisted, and an
*idle-armed* session (no Instagram at all) still died at ~3 m 48 s — so the kill is unconditional
for background apps and no standard exemption stops it. Fix in `FetchSpikeService`:
`armForeground()` runs the service as a **foreground service with an ongoing silent notification**
(`IMPORTANCE_MIN`), retried from the `BUBBLE_SHOW` path for the API 31+ foreground-start rule and
torn down in `onUnbind`/`onDestroy`. Device check on the fixed build: `isForeground=true`,
`startForegroundCount=1`, uid reported as `PROC_STATE_PERSISTENT` / `SYSTEM_ALLOW_LISTED`, and
heartbeats continued past the previous 210 s death mark. Full evidence, the measured onboarding
targets and the remaining soak: `V3.2_SESSION_CONTEXT.md` §6.

Mitigations landed in the recovery session:
- **Foreground service against the vendor power manager** — `armForeground()` /
  `disarmForeground()`, channel `downi_fetcher`, id `3342`, `foregroundServiceType="dataSync"` in
  the manifest, state exposed as `fgs=true/1` in the heartbeat. **Device-tested: it doubles
  survival (159 s/220 s → 328 s) but does not stop the kill** (see the B6 block above).
- `DowniBubble.isShown()` now asks the window manager instead of trusting its own flag, and
  `show()` rebuilds the view when the OS dropped it (`BUBBLE_WINDOW_LOST`) — this is the
  "bubble silently vanished, taps fell through" failure.
- Every delayed chain step runs through `postStep()` so a throwable ends the run
  (`CHAIN_STEP_ERR`) instead of killing the process; the tap path is fenced
  (`BUBBLE_TAP_ERR`) and `runChain` call sites are fenced (`CHAIN_ERR`).
- `onUnbind()` logs `SERVICE_UNBIND`, which is what tells a clean a11y unbind apart from a
  hard kill.
- Liveness forensics so the next death explains itself: `HEARTBEAT` every 30 s
  (`uptime_s`, `heap_mb=used/max`, `session`, `dumps`, `chain`, `bubble`), `TRIM_MEMORY level=`

## DOWNI CORE — the v3.2 target architecture (owner-approved, 2026-09-25)

**What the Core is.** A stateful ambient control that lives over Instagram and TikTok: it wakes when a

### Core invariants (hard guards — asserted in code, checked in every review)

1. **Detection ≠ download.** Nothing fires on detection; only a deliberate tap starts a job.
2. **No percent text in the Core.** Progress lives on the perimeter only (sheet 4).
3. **Edge attraction is never a forced snap.** The Core stays where the hand left it (sheet 5).
4. **The Core never writes files, jobs or the Vault.** `DowniDownloadService` remains the single source
   of truth; `CoreJobBinding` is a read-only observer.
5. **The duplicate check happens before the tap**, not after it (sheet 8 §5).
6. **No fake states.** If no video is detected the Core shows idle and says nothing (honesty rule).
