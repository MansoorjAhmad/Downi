### W1 — the snap's deformation: **two real defects found and fixed (2026-09-28)**

This started as a measurement. `tools\core_state_audit.py`'s M5 verdict measured only the ring's *aspect*
(`rx/ry`), and `ry`'s chord solve is ill-conditioned on this art — so the claim dead-ended on a number it
never needed. The contact axis of a left-edge snap is the **row**, and `rx` (the pair of ring crossings on
the centre row) was already measured every frame; nothing read it. So:

- **The instrument.** `touch_verdicts` now reports the **contact axis** — `rx` across the edge step
  against the pass's own rest baseline, with the envelope's own trace — plus a **coverage guard**: if the
  tracker held `rx` on fewer than half the frames, it prints *NOT DECIDED HERE* instead of a number. The
  verdict line now says how many claims went undecided, and the `settle` claim got the same guard (it
  used to print **PASS off a fallback value having measured zero frames** — a hollow PASS on the M8 pass).
- **The bug.** `DowniCore.finishDrag` inferred the contact axis as `horizontalHit = (nearX != lp.x)`. A
  finger that drags the Core flush to an edge leaves `moveTo` clamped, so `nearX == lp.x` — and a
  **left-edge hit was then deformed as if it were a vertical one**. Measured in the pass's own frames: at
  the envelope's peak the Core *widened* on the row (membrane inner extent 95 → 103 px, **+8 %**) where
  sheet C3 asks for a flattening. Fixed: the axis now comes from which edge is in range (`magnetX`),
  corner case documented. `BUILD SUCCESSFUL`, **17 suites / 117 tests / 0 failures** with the fix.
- **The second bug**, found while chasing the first: `CoreHost.drawArt` set the alpha on `p` and drew with
  `artPaint`, which never gets one — so the one shipping fade the static path owns, **RESUMING's
  `barAlpha`** ("the flow returns smoothly"), was a hard cut. Fixed on `artPaint`; same green build.
- **Device-confirmed the same day** (`DEVICE_TEST.md` §0l): `CORE_SQUASH t=0.74 env=0.071957536
  sx=0.9280425` — the row flattens on a left-edge snap — and the view's own draw count climbing
  9 → 13 → 17. The *pixel* instrument cannot add to that yet: the recorder drops the animation's frames
  (19 byte-identical frames across one snap, measured — §0l-5), so the deformation is proven the way
  position claims already are, by the service's own account.

### W2 — the Reach on a real session: it fires, and the pixels' limit is stated (2026-09-28)

A new rig script (`tools\core_reach.ps1`) relaunches, puts the Core on screen, opens the platform app on a
video, records 7 s, taps the Core's centre once, pulls the video and greps the service log. What it found:

- **A session engages the Reach** — `CORE_TAP session=com.zhiliaoapp.musically action=FETCH state=detected`
  → **`REACH_BEGIN core=540,1168`** (the live Core's own centre).
- **TikTok is the surface that can carry one; Instagram's Reels view cannot.** Both the Reel URL and the
  `/reels/<id>/` permalink gave `STEP3_DUMP… confidence=NONE note=no_url_or_id_in_tree`, so the Core
  honestly refuses there (`CORE_TAP session=null` → `CORE_TAP_NO_SESSION`) — the tap is not broken, the
  tree simply offers nothing to resolve.
- **A session without a share row still fails honestly**: `CHAIN_SCAN share=0 → CHAIN_NO_SHARE_CLICK →
  RUN_END delivered=false ms=149`, no crash, nothing downloaded.
- **The tether's pixels remain unpictured, and this says why:** the chain aborted at 149 ms (only the grow
  phase could play), and a frame-difference probe cannot separate a thin filament from a *playing video* —
  the content changed 20 000–90 000 px per frame on its own (`test_out/_reach_probe.txt`). The tether's
  proof stays the service's own account (`DEVICE_TEST.md` §0n, §0g-2), which is the same instrument the
  position claims already prefer.
