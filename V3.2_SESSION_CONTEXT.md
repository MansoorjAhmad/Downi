**DOWNI Fetcher** = a floating DOWNI bubble over Instagram/TikTok only. Open IG/TikTok →
bubble appears → tap → it downloads the video that is on screen, in the background, while
the owner keeps watching. Bubble must be draggable anywhere and remember its position.

**The correction that must never be lost:** the Phase 0.5 "DOWNI drives the platform's own

**Owner ruling 2026-09-25 ~18:20 (after the 17:1x–18:03 session; read before proposing anything):**
the Fetcher is a **detector + Core + tap**. Specifically:
1. **Nothing downloads by itself.** `handoff=true` (the spike's auto-grab gate) is a *test-bench
   switch*, never product behaviour. A run that fires a grab without a tap is a bug, not a feature.
   The download starts **only** on the user's tap of the Core.
2. **The resolver is plumbing, not UX.** Do not present route chains, "chooser-first", fallback
   ladders or share-sheet automation as *the feature*; that is what the owner rejected as "that's

3. **The visible product surface is exactly five things** (owner's words, 2026-09-25): automatic
   background detection → the Downi Core control appears → tap it → the download runs in the
   background while the user keeps watching → progress stays synced across Core ⇄ notification ⇄

**What the device actually allows for the identity behind a tap (measured 2026-09-25, all four seams,

## 4. What changed in the recovery session (2026-09-25)

`DowniBubble.java`
- `isShown()` now returns truth (`attached && visible && view.isAttachedToWindow()`), not the
  remembered flag — the old flag could say "shown" forever after the OS dropped the window,
  which is how the bubble "silently vanished" and taps began falling through to the app below.
- `show()` detects `attached && !windowAlive()` and **rebuilds** the view (`BUBBLE_WINDOW_LOST
  rebuild=1`) — re-adding the same View never regained touch on this ROM.
- `detach()` added (`removeViewImmediate`); `destroy()` uses it.

`FetchSpikeService.java`
- `postStep(Runnable, delay)` fences **every** delayed chain step plus the clipboard/focus
  follow-ups: a throwable ends the run (`CHAIN_STEP_ERR`) instead of killing the process.
- The bubble tap path is fenced (`BUBBLE_TAP_ERR`), and both `runChain` call sites are fenced
  (`CHAIN_ERR`).
- `onUnbind()` added → logs `SERVICE_UNBIND` (the line that tells a clean a11y unbind apart
  from a hard kill) and destroys the bubble.
- **Liveness forensics:** `HEARTBEAT` every 30 s (`uptime_s`, `heap_mb=used/max`, `session`,
  `dumps`, `chain`, `bubble`), plus `onTrimMemory` → `TRIM_MEMORY level=` and `onLowMemory` →
  `LOW_MEMORY`. The last line of the next log now says what the process was doing when it went.

`tools\fetch_diag.ps1` added — one command that pulls the whole forensic picture (crash buffer,
events, a11y state, process, WMS windows, battery whitelist, spike-log tail) and can re-arm the
service. Use it *before* guessing.

Verified: `gradlew assembleDebug` → **BUILD SUCCESSFUL** (177 tasks) with these changes, and the
APK is signed with the prod cert (`CN=Manso, O=OmniDownloader`, SHA-256 `4311…785e5`) at
`android\app\build\outputs\apk\debug\app-spike-signed.apk`.

## 6. B6 verdict — the death is the vivo power manager, and it is fixable (2026-09-25)

**Cause (confirmed, not inferred):** vivo's **Application Behavior Engine**
(`com.vivo.abe` / `com.vivo.applicationbehaviorengine`; `com.vivo.pem` is the power/energy
manager and `vivo.app.epm.IExceptionPolicyManager` its policy object) force-stops apps it judges
to be burning power in the background. Its own signature in the app-management log:

```
09-25 10:15:48.265  1625  2732 I am_kill : [0,11208,com.omnidownloader.app,100,stop com.omnidownloader.app due to stop by com.vivo.abe]
```

A vendor force-stop **also clears `enabled_accessibility_services`**, which is why the Fetcher
could never come back on its own and the owner had to re-arm the switch by hand. Two captures of
the same death: **159 s** (10:13:09 → 10:15:48) and **~220 s** (`uptime_s=210` was its last
heartbeat).

**Everything standard was ruled out with evidence, not opinion:**

| Suspect | Verdict |
|---|---|
| H2 uncaught throwable | **dead** — `-b crash` newest FATAL is 09:01:31 (the known, already-fixed `StackOverflowError`); nothing after it |
| H3 memory | **dead** — `heap_mb=2..8/256` at every death; `TRIM_MEMORY level=5` is routine, `LOW_MEMORY` never fired |
| H4 overlay dropped | **real but separate** — handled by the `BUBBLE_WINDOW_LOST` rebuild; it does not kill the process |
| Doze / app standby | **ruled out** — package was in `deviceidle whitelist`, `RUN_IN_BACKGROUND` allowed, and `batterystats` showed only `2.02 mAh / cpu=1.05 (28 s 96 ms)` for the whole uid |
| "being idle is safe" | **no** — an idle-armed session (no Instagram at all) still died at ~3 m 48 s; the kill is **unconditional for backgrounded apps**, activity only moves the time-to-threshold |

**The fix (implemented, `FetchSpikeService`):** run the accessibility service as a **foreground
service with an ongoing notification** — an ongoing FGS notification is the one signal every
vendor power manager reads as "the user can see this", and it additionally pins `oom_adj` at the
foreground-service level.

```java
armForeground();   // channel downi_fetcher, IMPORTANCE_MIN  →  startForeground(FGS_ID, notif)
```

- Called from `onServiceConnected()` (right after the heartbeat arms) **and** retried from the
  `BUBBLE_SHOW` path: API 31+ only permits a foreground start while the app is user-visible
  (`ForegroundServiceStartNotAllowedException` otherwise), and a visible overlay window is the
  strongest "visible" state we can hold.
- Torn down in `onUnbind()` / `onDestroy()` (`FGS_STOP`).
- **No new permissions:** the manifest already had `FOREGROUND_SERVICE`,
  `FOREGROUND_SERVICE_DATA_SYNC` and `POST_NOTIFICATIONS`; the service tag gained
  `android:foregroundServiceType="dataSync"`.
- Liveness line now carries it: `HEARTBEAT … fgs=true/1` (armed/tries).

**`com.vivo.pem` (PowerEffectManager) decides, `com.vivo.abe` (AppBehaviorEngine) enforces.**
Note also the repeated `am_pss` samples on us (10:34:04, 10:35:44, 10:37:59) — the system was
re-evaluating us as a victim well before the kill, i.e. we are on a policy list, not tripping a
one-off heuristic.

- `dumpsys activity services`: `startForegroundCount=1`, `isForeground=true`,
  `foregroundId=3342`, and the part that matters most —
  `infoAllowStartForeground=[… uidState: PER ; code:PROC_STATE_PERSISTENT ;
  tempAllowListReason:<reasonCode:SYSTEM_ALLOW_LISTED, duration:9223372036854775807>]`.
  Because the a11y service is system-bound, our uid is treated as **persistent** and allow-listed
  with no expiry.
- The notification is genuinely *visible* (not merely registered):
  `test_out\vivo_fgs_notif.png` — DOWNI → "DOWNI Fetcher is ready", filed under **Silent**.
- Shade open/close proved the loop still behaves under FGS: `BUBBLE_HIDE pkg=com.android.systemui`
  → `BUBBLE_SHOW pkg=com.instagram.android on_target=true`.

**CONCLUSION (corrected): the foreground service is necessary but NOT sufficient.** It is kept — it
demonstrably extends life and it is right for the product anyway (progress notification, LMK
protection) — but the honest verdict is that **B6 is still red on this ROM**: `com.vivo.abe`
force-stops a backgrounded app that has a foreground service, a persistent uid, a visible
notification *and* a device-idle whitelist, and it wipes `enabled_accessibility_services` when it
does. The remaining lever is **user-side, exactly as dontkillmyapp says**: vivo's own list
(*Settings → Battery → Background power consumption management → DOWNI → allow*, Autostart ON,
Battery unrestricted, Lock in Recents) is what takes an app out of `com.vivo.pem`'s kill policy.
Run that experiment before spending more code here — if it does not work either, the honest
answer to the owner is that zero-touch background Fetcher cannot be guaranteed on this ROM, and
the fallback has to be "keep DOWNI in the foreground" or "download while the screen is on".

only `ExternalCallService`. `dumpsys epm` (binder `vivo.app.epm.IExceptionPolicyManager`) lists
*only* crash / hang / ANR / canary / vm / fdleak policies — **no background-power handler**, and
it never mentions our package, so the killer's logic lives inside ABE itself. `vivo_behavior_service`
returns "No shell command implementation" for both `cmd` and `dumpsys`. Therefore no
`settings put`, no `cmd`, no `dumpsys` writing and no deep link can lift this policy: the levers
are the foreground service (kept — buys time) and the owner's own toggles (the experiment).

External corroboration: dontkillmyapp.com rates vivo **3/5 💩, "No known solution on dev end
yet"** — nothing a normal app can *call* fixes this; a foreground service is the only lever that
has consistently worked for other developers on vivo/Funtouch.

**Tooling and process lessons (these cost real time — do not repeat them):**

- **`adb logcat -b events` rotates within minutes on this ROM.** Read kills with `-b all`.
  `tools\fetch_diag.ps1` is fixed accordingly (`KILL/PROC EVENTS` now reads `-b all`).
- Watch **`powercontrol|vivo\.pem`**, not just our own package: the trigger
  (`action.vivo.powercontrol` from `com.vivo.pem`) lands ~2 s before the kill and is the leading
  indicator of a vendor stop. Added to `fetch_diag.ps1`'s KILL/PROC filter.
- **The `$` in a component name is expanded by the *device* shell**, so
  `am start -n com.android.settings/.Settings$SelfStartListActivity` silently degrades to
  `cmp=com.android.settings/.Settings` and starts the wrong page. Quote it for the device
  (`am start -n 'pkg/.Settings$Foo'`) — a wrong-page launch looks like "the page doesn't exist".
- Background jobs outlive a platform command: `soak_watch.ps1`, `ig_scroll_loop.ps1` and the
  logcat killwatch are all started with `Start-Process` and read back later. A kill can therefore
  be captured unattended, which is the only way the `-b all` truth ever surfaces.
- **`.gitignore:10` is `tools/`** and `:41` is `*.log` — the diagnostic scripts and soak records are
  not tracked. If the tools are to survive the next machine, that entry has to be revisited.
- A kill can be **silent and unattended**; a one-shot capture misses it. Use
  `tools\soak_watch.ps1 -Minutes 30` — it timestamps `ALIVE/DEAD`, the a11y setting and the newest
  heartbeat every 20 s, so a death is on record even with nobody watching.
- Dump cadence is the "power" fuel ABE reacts to: `STEP3_DUMP_2` on a *stable* Reels tree means
  ~1 dump/min, while dump-churn is ~20/min. Keeping idle cost near zero is both good product
  behaviour and the best defence against the vendor governor.
